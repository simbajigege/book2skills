# Workflow 规格模板

当用户要求完整拆解、节点提示词、工具配置或工程实现规格时，使用本模板。删去不适用的部分，不为填满模板虚构节点、工具或状态。

## 1. 转换摘要

- 源对象：Skill、Prompt、SOP 或 Agent 流程的名称与位置
- Workflow 目标：最终解决什么问题
- 目标平台：指定平台或平台无关
- 主体粒度：批次、单对象、会话或事件
- 主节点数：不含或包含共享子工作流时分别说明
- 主链路：一行表示
- 关键回路：补充信息、校验修复、人工审批等
- 正式产物：事实源与派生产物

## 2. 源规则覆盖表

| 源规则或步骤 | Workflow 承接位置 | 实现方式 | 验收方法 |
|---|---|---|---|
| 必需输入 | 初始化节点 | Schema | 缺失时阻断 |

覆盖：输入、事实来源、关键判断、工具、输出、禁止事项、权限和完成检查。

## 3. Workflow 图

先画主链路，再标分支和回路：

```text
初始化
→ 规范化
→ 单对象循环
   → 获取材料
   → 领域分析
   → 证据建模
   → 决策或评分
   → 产物组装与校验
→ 汇总
```

图中标明 `partial`、`failed`、`needs_human` 和回退目标。只有真正可并行的节点才画成并行分支。

## 4. 节点总表

| ID | 节点 | 类型 | 主要责任 | 输入 | 输出 | 工具 | 失败去向 |
|---|---|---|---|---|---|---|---|
| N1 | 示例节点 | LLM | 形成一种稳定判断 | `normalized_input` | `decision` | 无 | N0 或 partial |

## 5. 单节点规格

每个节点使用以下结构：

### N<n>：节点名称

- **目标：**本节点唯一主要责任。
- **类型：**确定性、LLM、工具、人工或路由。
- **触发条件：**何时进入。
- **输入：**字段、来源和前置状态。
- **工具：**只列本节点允许使用的工具及用途。
- **处理规则：**判断顺序、禁止事项和停止条件。
- **输出：**结构化字段及 Schema。
- **完成标准：**什么结果可以进入下游。
- **异常处理：**技术失败、数据不足、冲突和回退路径。
- **幂等与缓存：**重复执行时如何识别和复用。

LLM 节点再提供节点 Prompt：

```text
任务角色与本节点目标

输入：
{{structured_inputs}}

执行：
1. 判断顺序；
2. 证据和推断边界；
3. 缺失、冲突和空结果处理；
4. 停止条件。

只输出符合 {{output_schema}} 的 JSON，不输出额外说明。
```

确定性和工具节点通常不需要 Prompt；写清算法、命令、API 契约或平台节点配置。不要为了模板完整而给每个节点添加 LLM。

## 6. 共享约束 Prompt

只放所有 LLM 节点真正共享的规则：

```text
你每次只处理一个明确作用域。

必须遵守：
1. 区分已确认事实、有限推断和未知信息；
2. 所有关键结论可追溯到输入或来源 ID；
3. 不把上层背景直接当作当前对象结论；
4. 证据不足进入 limitations 或降低 confidence，不得编造；
5. 不输出正式 Schema 未声明的字段；
6. 只输出结构化数据。
```

根据源 Skill 替换这些通用占位规则，不保留与业务无关的条目。

## 7. 共享子工作流

### SW<n>：共享能力名称

- **复用方：**哪些节点调用。
- **共享机制：**被复用的是搜索、解析、构建还是其他机制。
- **不负责：**明确不在共享层做的业务结论。
- **权限：**允许使用的工具和外部副作用。
- **缓存键：**作用域、输入哈希、规范 URL、版本或时间。
- **预算：**最大查询、页面、轮次、时间或费用。

推荐请求契约：

```json
{
  "request_id": "scope-capability-01",
  "request_type": "fixed-enum",
  "goal": "本次调用要解决的问题",
  "questions": [],
  "known_context": {},
  "constraints": [],
  "preferred_tools_or_sources": [],
  "budget": {},
  "stop_condition": "何时停止"
}
```

推荐响应契约：

```json
{
  "request_id": "scope-capability-01",
  "status": "complete",
  "data_or_evidence": [],
  "source_updates": [],
  "conflicts": [],
  "unresolved_questions": [],
  "limitations": []
}
```

需要网页调研时，可将共享能力设计为：

```text
调研请求
→ 查询规划
→ Web Search
→ URL 去重与来源排序
→ Web Open
→ 证据提取与来源登记
→ 充分性判断
↺ 只对会改变下游结论的关键缺口补查
```

搜索摘要只用于发现页面；分析节点消费证据包，不直接继承搜索摘要形成的结论。

## 8. 运行状态与数据

推荐最小运行信封：

```json
{
  "scope_id": "stable-id",
  "node_id": "N1",
  "status": "complete",
  "data": {},
  "source_ledger": [],
  "limitations": [],
  "attempt": 1,
  "generated_at": "ISO-8601"
}
```

明确：

- 哪些字段是事实源；
- 哪些字段只用于 Workflow 内部；
- 哪些字段必须进入最终产物；
- 哪些数据可跨对象缓存，哪些结论必须按对象隔离；
- 版本、时间敏感数据和历史产物如何失效。

## 9. 路由与重试表

| 条件 | 状态 | 下一步 | 最大次数 | 停止结果 |
|---|---|---|---|---|
| 缺必需输入 | failed | 结束或请求用户 | 0 | failed |
| 非关键证据不足 | partial | 继续 | 0 | partial |
| 关键未知会改变决策档位 | retry | 定向补查 | 2 | partial/needs_human |
| 正式校验失败 | retry | 修事实源后重建 | 2 | failed/needs_human |

不要把所有错误都自动重试。外部写入、付费调用和高风险动作必须遵守原任务授权边界。

## 10. 构建与验收

说明：

1. 标准事实源如何组装；
2. 派生产物如何确定性生成；
3. Schema、字段、来源和跨字段约束如何校验；
4. 校验失败回到哪个上游节点；
5. 批次和单对象如何汇总状态；
6. 端到端完成条件。

最终检查：

- 每条源 Skill 核心规则有承接节点；
- 每个节点能独立观察输入、输出和失败原因；
- 同一机制的重复工具调用已评估是否适合抽象；
- 共享子工作流没有吞掉业务判断；
- LLM 不承担可以确定性完成的计算或校验；
- 所有循环有停止条件；
- 正式产物保持原数据契约和事实来源一致；
- 设计没有暗示未获授权的部署、发送、删除或外部写入。
